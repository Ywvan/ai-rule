# 生产实现方案设计

## 使用场景

当用户提供业务需求、产品需求、缺陷修复需求、数据口径调整需求、报表改造需求、外部接口对接需求，并要求理解需求、分析影响范围、输出后端实现方案时，使用本 Skill。

本 Skill 只负责：

- 理解需求
- 拆解业务口径
- 分析现有链路
- 输出生产可落地实现方案
- 标记不确定点
- 输出验证方案
- 判断是否适合进入 Codex 执行阶段

本 Skill 只输出生产可落地后端实现方案，以及是否建议进入 Codex 执行阶段。

本 Skill 不负责输出完整可复制给 Codex 的分轮执行任务。

如果用户需要可以直接复制给 Codex 执行的完整分轮任务，应切换到「Codex 分轮执行计划」Skill。

本 Skill 默认不直接修改代码。

## 总体原则

1. 先理解需求，再设计方案。
2. 先确认业务口径，再分析技术实现。
3. 不允许跳过需求理解直接写代码。
4. 分析深度优先于修改速度；允许扩大分析范围，不允许扩大修改范围。
5. 先找全调用链、数据流、SQL、权限、导出、任务和外部接口影响点，再输出最小落地方案。
6. 不允许为了展示能力做过度设计。
7. 不允许引入额外基础设施，除非需求明确要求。
8. 不允许修改接口协议、表结构、索引、Liquibase，除非方案中明确说明必要性和影响范围。
9. 所有不确定点必须标记为“不确定”，不能猜。
10. 涉及金额、出账、权限、状态流转、历史数据、外部接口时，必须单独列风险。
11. 涉及报表、分页、导出、COUNT、权限、多语言、索引时，必须单独分析性能和兼容性。
12. 输出必须可落地，避免泛化描述。
13. 如果没有读取代码或没有用户提供明确文件路径，不允许假设具体 Controller / Service / Mapper / 表 / 字段存在。
14. 只能基于用户已提供信息分析，并将需要代码确认的内容标记为“不确定”或“待第 1 轮代码调查确认”。

## GPT-5.6 执行模式兼容

本 Skill 兼容普通、max、Pro、Ultra 和子 Agent 执行方式。

本 Skill：

- 不强制指定模型；
- 不强制指定推理强度；
- 不强制启用 Ultra；
- 不禁止 Ultra；
- 不强制创建子 Agent；
- 不禁止创建子 Agent；
- 不固定子 Agent 数量；
- 不覆盖用户的并发、深度或模型配置。

执行模式只影响任务的推理、委派和并行方式，不得改变：

1. 用户明确的任务目标；
2. 当前 Skill 的职责；
3. 当前任务的只读或可写状态；
4. 当前已确认业务口径；
5. 当前修改范围和禁止修改范围；
6. 当前轮次、风险编号或 Review 范围；
7. 高风险业务语义的确认要求；
8. 当前 Skill 原有的停止条件；
9. 当前任务的验证和输出要求。

不得因为使用 max、Pro、Ultra 或子 Agent：

- 扩大修改范围；
- 跳过调查；
- 跳过验证；
- 将推荐理解视为已确认事实；
- 绕过 Review 只读限制；
- 自动进入下一轮；
- 顺手处理任务范围外的问题。

## 子 Agent 委派规则

Codex 可以根据任务复杂度，将能够独立完成的工作委派给子 Agent。

主 Agent 委派时必须明确：

- 子任务目标；
- 调查或修改范围；
- 当前是只读还是可写；
- 当前轮次或风险编号；
- 已确认事实；
- 不确定点；
- 允许修改范围；
- 禁止修改范围；
- 需要返回的文件、符号、调用链或测试证据；
- 验收条件。

不得假设子 Agent 自动拥有主 Agent 的完整业务上下文和修改权限。

子 Agent 发现新问题时：

- 可以报告问题和证据；
- 不得自行扩展为新的修改任务；
- 不得修改当前子任务之外的问题。

主 Agent 负责：

- 汇总子 Agent 结果；
- 处理结论冲突；
- 去除重复结论；
- 检查修改范围；
- 统一业务术语；
- 统一检查最终 diff；
- 执行最终验证；
- 遵守当前 Skill 的停止条件。

### 当前 Skill 执行边界

- 本 Skill 及其子 Agent 只允许调查现有链路并输出生产实现方案，不得直接修改代码、SQL、配置或数据库结构。
- 当前任务属于多轮计划时，必须继承用户指定的当前轮，不得替代分轮执行 Skill 自动进入实施或下一轮。

### 并行修改规则

本 Skill 只调查现有链路并输出生产实现方案。以下规则仅用于设计后续实现阶段的并行修改边界，不授权主 Agent 或子 Agent 直接修改代码、SQL、配置或数据库结构。

并行修改必须满足：

1. 子任务职责清晰；
2. 修改范围可以明确归属；
3. 不得无协调地同时修改同一个文件；
4. 不得同时修改同一段业务逻辑；
5. 不得按不同业务口径修改同一链路；
6. 主 Agent 必须统一检查和验证结果。

以下共享内容必须指定单一修改负责人，或者由主 Agent 统一修改：

- 公共接口协议；
- 公共 DTO、VO、请求和响应结构；
- 公共枚举；
- 数据库表结构；
- Liquibase；
- 公共 SQL 片段；
- 权限和租户隔离；
- 金额、支付和结算口径；
- 状态机；
- MQ 消息结构；
- 公共基础组件；
- 多个模块共同依赖的配置。

本 Skill 不承担任何并行写入；后续实现阶段是否使用 Ultra 或子 Agent，由对应实现任务在其授权范围内决定。

## 图片、截图与流程图证据

当用户提供需求截图、页面截图、流程图、时序图、数据库截图或接口文档截图时，应将可见内容纳入分析证据。

必须区分：

- 图片中明确可见的文字、字段和流程；
- 根据布局、连线或箭头推断的关系；
- 图片中没有展示、无法确认的业务语义。

图片可以用于确认：

- 页面字段；
- 系统参与方；
- 调用方向；
- 流程节点；
- 表和字段名称；
- 明确标注的规则。

不得仅根据图片推断：

- 未展示的默认值；
- 权限和租户范围；
- 金额和结算口径；
- 异常处理；
- 历史数据规则；
- 完整枚举值域；
- 未明确表达的同步、异步和事务边界。

图片和文字需求冲突时，必须列出冲突点，不得静默选择其中一个作为最终口径。

该规则不要求每个任务都使用图片能力。

## 需求语义判断规则

1. 历史代码、历史 SQL、默认值、兜底逻辑、硬编码限制只作为现状信息；它们不自动等同于业务语义，也不自动等同于缺陷。
2. 判断历史实现时必须区分证据等级：需求文档、字段注释、枚举定义、接口说明、测试用例、产品确认记录、历史提交说明、线上配置、权限或租户隔离设计属于明确证据；现有 SQL、if/else、默认值、硬编码、兜底、固定排除、白名单或黑名单属于弱证据；仅凭命名或旧写法推断属于无证据。
3. 弱证据不能直接作为“必须保护业务语义”的依据；无证据时必须标注“不确定”，但仍要给出当前最合理的参考建议、替代方案、风险说明和验证方式。
4. 当用户明确需求与历史实现冲突时，必须列出用户需求、历史实现、冲突点、历史实现证据等级、推荐修改方案、影响范围和验证方式；不得用“保持原有逻辑”“不改变已有业务语义”“降低业务变化”“历史 SQL 如此”直接否定用户明确需求。
5. 不确定点分为非阻塞和阻塞型：普通查询筛选、报表筛选、列表过滤、导出过滤、展示字段、文案映射、非核心统计口径通常非阻塞，应继续输出推荐方案；涉及权限控制、租户隔离、支付、结算、对账、状态流转、定时任务或批量处理默认范围、历史数据迁移、外部接口协议时属于阻塞型，不得未确认直接执行高风险变更，但仍可输出参考方案和 Codex plan。
6. 高风险按变更影响判断，不按字段名称机械判断：报表展示金额不等同于支付结算风险，列表状态筛选不等同于状态流转变更，业务查询条件不等同于权限或租户隔离变更。
7. 新增可选查询条件、报表筛选条件、列表过滤条件时，默认语义是传值才过滤、不传不限制，空值、空集合、空字符串不生成过滤条件或反向排除条件；该规则不得直接套用到权限控制、租户隔离、状态流转、金额计算、结算、支付、定时任务、批量处理、数据初始化或历史迁移。
8. 用户明确需求可以覆盖历史实现，但必须保持最小改动；不得静默修改详情、导出、统计、权限 wrapper、定时任务、批量处理、对账、结算、支付或公共 SQL 片段，明显存在口径一致性关系的链路应列为建议同步检查项、待确认影响范围或推荐同步修改项。

## 输出收敛规则

1. 对简单、局部、低风险需求，保持输出简洁，只给必要分析、推荐方案和验证点。
2. 只有需求涉及历史固定排除、默认口径、公共 SQL、金额、状态、权限、结算、定时任务、批量处理，或用户明确要求调整历史逻辑时，才完整展开证据分层和冲突分析。
3. 不得因为存在普通不确定点，就把简单任务升级成复杂方案或拒绝给出参考建议。
4. 不得为了展示分析过程而列出与本次需求无关的高风险链路。
5. 与本需求无关的固定模板章节可以简写为“不涉及，原因：xxx”，但不得删除风险点清单、验证方案、上线与回滚方案、不确定点、是否建议进入 Codex 执行阶段等关键章节。

## 禁止行为

不允许：

- 直接开始改代码。
- 直接生成大段代码。
- 直接假设数据库字段含义。
- 直接假设已有接口行为。
- 直接假设权限口径。
- 直接假设历史数据可以无脑补偿。
- 直接建议新增表、新增字段、新增索引，除非说明必要性、影响范围和替代方案。
- 顺手重构、改名、抽方法、优化无关逻辑。
- 把多个问题混在一个方案中处理。
- 用“应该没问题”“大概率”“一般来说”代替证据。
- 输出空泛的架构图、分层描述、DDD 概念，除非对本需求有直接价值。

## 输出要求

默认输出普通 Markdown 正文。

不要在最外层包裹 ```markdown。

路径、类名、方法名、字段名、SQL 片段、枚举值使用行内反引号。

如果必须输出 SQL 或伪代码，可以使用缩进文本，避免嵌套多层代码块。

输出内容必须按以下结构组织。

必须保留整体章节结构。

与本需求无关的章节可以简写为“不涉及，原因：xxx”。

不得删除以下关键章节：

- 风险点清单
- 验证方案
- 上线与回滚方案；若确实不涉及生产数据、任务、外部接口、批量补偿，则必须说明“不涉及”
- 不确定点
- 是否建议进入 Codex 执行阶段

- 用户想解决什么问题
- 当前现象是什么
- 目标结果是什么
- 这个需求影响的是查询展示、保存、创单、结算、同步、报表、权限，还是其他链路

格式：

- 需求目标：
- 当前问题：
- 目标结果：
- 影响链路：

## 2. 问题本质

说明这个问题的根因，而不是只描述表面现象。

要求：

- 区分“页面展示问题”和“真实业务数据问题”
- 区分“查询口径问题”和“落库口径问题”
- 区分“新增数据问题”和“历史数据问题”
- 区分“接口返回问题”和“下游消费问题”

- 入参来源

- 下游接口入参

- 结算落数字段

- 异常回滚

### 4.3 报表类需求

- 报表编码

- 导出查询

## 跨仓库与跨服务影响

当需求明确涉及多个仓库或多个服务时，必须建立仓库级影响清单。

每个仓库分别说明：

- 仓库或服务名称；
- 在业务链路中的职责；
- 只读调查范围；
- 建议修改范围；
- 明确不修改范围；
- 对外提供的接口、MQ、数据或配置；
- 依赖的接口、MQ、数据或配置；
- 独立验证方式；
- 联合验证方式。

不得因为多个仓库可访问而默认修改所有相关仓库。

只修改完成当前需求所必需的仓库。

### 跨仓库共享语义

以下内容必须先统一语义，再分别实现：

- 请求和响应协议；
- DTO 和枚举值；
- MQ Topic、Tag 和消息结构；
- 数据库字段和数据口径；
- 权限和租户标识；
- 金额、支付和结算口径；
- 状态和值域；
- 配置项含义。

不同仓库、不同 Agent 不得分别猜测共享业务语义。

主 Agent 必须为每项跨仓库共享语义指定单一确认负责人，并记录已确认口径、依赖仓库和不确定点。

| 共享语义 | 确认负责人 | 已确认口径 | 依赖仓库 / 服务 | 不确定点 |
|---|---|---|---|---|

### 跨仓库验证、发布与回滚顺序

跨仓库方案必须说明：

1. 协议或数据语义确认；
2. 提供方修改；

## 特殊规则

### A. 报表需求特殊规则

如果是报表需求，必须额外检查：

- 报表编码
- 当前数据源
- 目标数据源
- 字段映射
- 权限字段
- 多语言字段
- 分页查询
- 导出查询
- COUNT 查询
- 排序字段
- 是否存在大租户数据量风险
- 是否需要索引
- 是否需要 EXPLAIN
- 是否影响 Excel 行上限

不能只输出字段映射。

必须明确：

- 页面查询和导出是否共用 SQL
- COUNT 是否单独优化
- LIMIT 是否能限制最终返回给 JVM 的行数
- 是否存在先全量查再内存分页的风险

### B. 出账 / 结算需求特殊规则

如果涉及出账、结算、支付主体、公司 OID、法人、账套、费用归属，必须额外检查：

- 展示字段是否正确
- 创单传给下游的字段是否正确
- 订单落库字段是否正确
- 结算落数字段是否正确
- 历史数据是否需要修正
- 是否影响已出账数据
- 是否影响对账
- 是否影响财务报表

不能只修列表接口。

### C. 权限需求特殊规则

如果涉及权限，必须额外检查：

- 可见权限
- 数据权限
- 管理范围
- 指定人员角色
- 指定部门角色
- 直属领导
- 直属下属
- 部门穿透
- 公司 / 法人 / 账套
- 申请人 / 预订人 / 出行人字段语义

必须明确字段别名是否和权限框架一致。

### D. 外部接口对接特殊规则

如果涉及外部接口，必须额外检查：

- 是否已有 client
- 是否已有签名 / 鉴权封装
- 是否已有重试机制
- 是否已有请求响应日志
- 是否已有失败记录表
- 是否需要异步任务
- 是否需要补偿任务
- 是否需要人工重试能力
- 是否需要幂等键

不能只写“调用第三方接口”。

### E. 数据补偿特殊规则

如果涉及历史补偿，必须额外检查：

- 补偿范围是否可控
- 是否按租户分批
- 是否按时间分批
- 是否幂等
- 是否有 dry-run 查询
- 是否有执行前 COUNT
- 是否有执行后核对
- 是否有回滚 SQL
- 是否有灰度租户

不能直接给 UPDATE，不给核对 SQL。

### F. SQL / 索引特殊规则

如果涉及 SQL 性能，必须额外检查：

- WHERE 条件是否包含 `tenant_id`
- 是否包含时间范围
- 是否能使用已有索引
- 是否有函数包裹索引字段
- 是否有隐式类型转换
- 是否有低选择性字段放在索引前部
- 是否存在大范围 ORDER BY
- 是否存在临时表 / filesort
- 是否存在 JOIN 放大
- 是否存在 DISTINCT 掩盖重复数据问题

没有 EXPLAIN 时：

- 可以给索引建议
- 不允许直接要求修改 Liquibase
- 必须标记“需要 EXPLAIN 验证”
