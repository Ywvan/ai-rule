# 生产实现方案设计

## 使用场景

当用户提供业务需求、产品需求、缺陷修复需求、数据口径调整需求、报表改造需求、外部接口对接需求，并要求理解需求、分析影响范围、输出后端实现方案时，使用本 Skill。

本 Skill 只负责：

- 理解需求
- 拆解业务口径
- 分析现有链路
- 输出生产可落地实现方案
- 标记不确定点
- 输出验证方案
- 判断是否适合进入 Codex 执行阶段

本 Skill 只输出生产可落地后端实现方案，以及是否建议进入 Codex 执行阶段。

本 Skill 不负责输出完整可复制给 Codex 的分轮执行任务。

如果用户需要可以直接复制给 Codex 执行的完整分轮任务，应切换到「Codex 分轮执行计划」Skill。

本 Skill 默认不直接修改代码。

## 总体原则

1. 先理解需求，再设计方案。
2. 先确认业务口径，再分析技术实现。
3. 不允许跳过需求理解直接写代码。
4. 分析深度优先于修改速度；允许扩大分析范围，不允许扩大修改范围。
5. 先找全调用链、数据流、SQL、权限、导出、任务和外部接口影响点，再输出最小落地方案。
6. 不允许为了展示能力做过度设计。
7. 不允许引入额外基础设施，除非需求明确要求。
8. 不允许修改接口协议、表结构、索引、Liquibase，除非方案中明确说明必要性和影响范围。
9. 所有不确定点必须标记为“不确定”，不能猜。
10. 涉及金额、出账、权限、状态流转、历史数据、外部接口时，必须单独列风险。
11. 涉及报表、分页、导出、COUNT、权限、多语言、索引时，必须单独分析性能和兼容性。
12. 输出必须可落地，避免泛化描述。
13. 如果没有读取代码或没有用户提供明确文件路径，不允许假设具体 Controller / Service / Mapper / 表 / 字段存在。
14. 只能基于用户已提供信息分析，并将需要代码确认的内容标记为“不确定”或“待第 1 轮代码调查确认”。

## 禁止行为

不允许：

- 直接开始改代码。
- 直接生成大段代码。
- 直接假设数据库字段含义。
- 直接假设已有接口行为。
- 直接假设权限口径。
- 直接假设历史数据可以无脑补偿。
- 直接建议新增表、新增字段、新增索引，除非说明必要性、影响范围和替代方案。
- 顺手重构、改名、抽方法、优化无关逻辑。
- 把多个问题混在一个方案中处理。
- 用“应该没问题”“大概率”“一般来说”代替证据。
- 输出空泛的架构图、分层描述、DDD 概念，除非对本需求有直接价值。

## 输出要求

默认输出普通 Markdown 正文。

不要在最外层包裹 ```markdown。

路径、类名、方法名、字段名、SQL 片段、枚举值使用行内反引号。

如果必须输出 SQL 或伪代码，可以使用缩进文本，避免嵌套多层代码块。

输出内容必须按以下结构组织。

必须保留整体章节结构。

与本需求无关的章节可以简写为“不涉及，原因：xxx”。

不得删除以下关键章节：

- 风险点清单
- 验证方案
- 上线与回滚方案；若确实不涉及生产数据、任务、外部接口、批量补偿，则必须说明“不涉及”
- 不确定点
- 是否建议进入 Codex 执行阶段

## 特殊规则

### A. 报表需求特殊规则

如果是报表需求，必须额外检查：

- 报表编码
- 当前数据源
- 目标数据源
- 字段映射
- 权限字段
- 多语言字段
- 分页查询
- 导出查询
- COUNT 查询
- 排序字段
- 是否存在大租户数据量风险
- 是否需要索引
- 是否需要 EXPLAIN
- 是否影响 Excel 行上限

不能只输出字段映射。

必须明确：

- 页面查询和导出是否共用 SQL
- COUNT 是否单独优化
- LIMIT 是否能限制最终返回给 JVM 的行数
- 是否存在先全量查再内存分页的风险

### B. 出账 / 结算需求特殊规则

如果涉及出账、结算、支付主体、公司 OID、法人、账套、费用归属，必须额外检查：

- 展示字段是否正确
- 创单传给下游的字段是否正确
- 订单落库字段是否正确
- 结算落数字段是否正确
- 历史数据是否需要修正
- 是否影响已出账数据
- 是否影响对账
- 是否影响财务报表

不能只修列表接口。

### C. 权限需求特殊规则

如果涉及权限，必须额外检查：

- 可见权限
- 数据权限
- 管理范围
- 指定人员角色
- 指定部门角色
- 直属领导
- 直属下属
- 部门穿透
- 公司 / 法人 / 账套
- 申请人 / 预订人 / 出行人字段语义

必须明确字段别名是否和权限框架一致。

### D. 外部接口对接特殊规则

如果涉及外部接口，必须额外检查：

- 是否已有 client
- 是否已有签名 / 鉴权封装
- 是否已有重试机制
- 是否已有请求响应日志
- 是否已有失败记录表
- 是否需要异步任务
- 是否需要补偿任务
- 是否需要人工重试能力
- 是否需要幂等键

不能只写“调用第三方接口”。

### E. 数据补偿特殊规则

如果涉及历史补偿，必须额外检查：

- 补偿范围是否可控
- 是否按租户分批
- 是否按时间分批
- 是否幂等
- 是否有 dry-run 查询
- 是否有执行前 COUNT
- 是否有执行后核对
- 是否有回滚 SQL
- 是否有灰度租户

不能直接给 UPDATE，不给核对 SQL。

### F. SQL / 索引特殊规则

如果涉及 SQL 性能，必须额外检查：

- WHERE 条件是否包含 `tenant_id`
- 是否包含时间范围
- 是否能使用已有索引
- 是否有函数包裹索引字段
- 是否有隐式类型转换
- 是否有低选择性字段放在索引前部
- 是否存在大范围 ORDER BY
- 是否存在临时表 / filesort
- 是否存在 JOIN 放大
- 是否存在 DISTINCT 掩盖重复数据问题

没有 EXPLAIN 时：

- 可以给索引建议
- 不允许直接要求修改 Liquibase
- 必须标记“需要 EXPLAIN 验证”
