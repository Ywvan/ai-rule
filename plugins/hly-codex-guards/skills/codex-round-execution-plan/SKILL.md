# Codex 分轮执行计划

## 使用场景

当用户已经有需求、问题分析或实现方案，并要求生成可以直接复制给 Codex 执行的任务计划时，使用本 Skill。

本 Skill 的目标是把方案拆成多轮可执行任务，控制 Codex 的改动范围和执行节奏。

## 总体原则

1. 每一轮只能处理一个明确目标。
2. 生成新的多轮计划时，第 1 轮默认只做代码调查，不允许修改代码。
3. 执行已有多轮计划时，以用户明确指定的当前轮为准；不得因为存在第 1 轮规则而重新回到调查轮，除非用户要求重新调查。
4. 不允许边分析边修改。
5. 分析深度优先于修改速度；允许扩大分析范围，不允许扩大修改范围。
6. 分析阶段可以多看调用链、数据流、SQL、Mapper、Service、Controller、Job、导出和权限逻辑；实施阶段只能改确认范围内的文件。
7. 不允许顺手优化、重构、改名、抽方法、调整无关代码。
8. 不允许修改接口协议、表结构、索引、Liquibase，除非任务明确要求。
9. 所有不确定点必须标记为“不确定”，不能猜。
10. 修改 SQL 前，必须先列出需要保持不变的业务口径。
11. 修改权限、金额、状态流转、出账、结算、历史数据前，必须先说明语义保护点。
12. 原问题没有验证通过前，禁止处理新发现的问题。
13. 每轮完成后必须输出本轮 diff 的语义保护 review。

## GPT-5.6 执行模式兼容

本 Skill 兼容普通、max、Pro、Ultra 和子 Agent 执行方式。

本 Skill：

- 不强制指定模型；
- 不强制指定推理强度；
- 不强制启用 Ultra；
- 不禁止 Ultra；
- 不强制创建子 Agent；
- 不禁止创建子 Agent；
- 不固定子 Agent 数量；
- 不覆盖用户的并发、深度或模型配置。

执行模式只影响任务的推理、委派和并行方式，不得改变：

1. 用户明确的任务目标；
2. 当前 Skill 的职责；
3. 当前任务的只读或可写状态；
4. 当前已确认业务口径；
5. 当前修改范围和禁止修改范围；
6. 当前轮次、风险编号或 Review 范围；
7. 高风险业务语义的确认要求；
8. 当前 Skill 原有的停止条件；
9. 当前任务的验证和输出要求。

不得因为使用 max、Pro、Ultra 或子 Agent：

- 扩大修改范围；
- 跳过调查；
- 跳过验证；
- 将推荐理解视为已确认事实；
- 绕过 Review 只读限制；
- 自动进入下一轮；
- 顺手处理任务范围外的问题。

## 子 Agent 委派规则

Codex 可以根据任务复杂度，将能够独立完成的工作委派给子 Agent。

主 Agent 委派时必须明确：

- 子任务目标；
- 调查或修改范围；
- 当前是只读还是可写；
- 当前轮次或风险编号；
- 已确认事实；
- 不确定点；
- 允许修改范围；
- 禁止修改范围；
- 需要返回的文件、符号、调用链或测试证据；
- 验收条件。

不得假设子 Agent 自动拥有主 Agent 的完整业务上下文和修改权限。

子 Agent 发现新问题时：

- 可以报告问题和证据；
- 不得自行扩展为新的修改任务；
- 不得修改当前子任务之外的问题。

主 Agent 负责：

- 汇总子 Agent 结果；
- 处理结论冲突；
- 去除重复结论；
- 检查修改范围；
- 统一业务术语；
- 统一检查最终 diff；
- 执行最终验证；
- 遵守当前 Skill 的停止条件。

### 当前 Skill 执行边界

- 主 Agent 和子 Agent 必须继承用户指定的当前轮、只读或可写状态、允许修改文件和禁止修改范围。
- 子 Agent 只完成被委派的当前轮子任务并返回证据，不得自动执行下一轮。
- 主 Agent 必须在当前轮完成后停止，等待用户验收。

### 并行修改规则

当前任务本身允许代码修改时，可以将相互独立的实现工作委派给子 Agent。

并行修改必须满足：

1. 子任务职责清晰；
2. 修改范围可以明确归属；
3. 不得无协调地同时修改同一个文件；
4. 不得同时修改同一段业务逻辑；
5. 不得按不同业务口径修改同一链路；
6. 主 Agent 必须统一检查和验证结果。

以下共享内容必须指定单一修改负责人，或者由主 Agent 统一修改：

- 公共接口协议；
- 公共 DTO、VO、请求和响应结构；
- 公共枚举；
- 数据库表结构；
- Liquibase；
- 公共 SQL 片段；
- 权限和租户隔离；
- 金额、支付和结算口径；
- 状态机；
- MQ 消息结构；
- 公共基础组件；
- 多个模块共同依赖的配置。

不强制主 Agent 唯一写入，也不禁止 Ultra 的并行实现能力。

## 跨仓库与跨服务执行规则

只有任务明确涉及多个仓库或多个服务时才启用本节。

必须先建立仓库级影响清单，逐个说明仓库职责、只读调查范围、允许修改范围、禁止修改范围、提供和依赖的接口 / MQ / 数据 / 配置、独立验证和联合验证。

不得因为仓库可访问就默认修改。只允许修改完成当前轮目标所必需的仓库。

请求和响应协议、DTO、枚举、MQ、数据库字段和数据口径、权限和租户标识、金额与结算口径、状态和值域、配置项含义，必须指定单一语义确认负责人。不同仓库和不同 Agent 不得分别猜测。

跨仓库轮次必须明确提供方、消费方、独立验证、联合验证、新旧版本兼容检查、发布顺序和回滚顺序。

## 已确认事实与中途修正

用户确认的任务目标、业务口径、修改范围和当前轮计划，是当前执行阶段的事实来源。

用户中途补充或修正要求时：

1. 只更新受影响的事实、当前轮或后续轮次；
2. 保留仍然有效的调查结果；
3. 保留未受影响的已确认业务口径；
4. 保留已经验证通过且未受影响的修改；
5. 不得无理由重新开始完整调查；
6. 不得无理由推翻未受影响的实现；
7. 必须说明新旧要求的冲突点；
8. 必须说明受影响的文件、轮次和验证项。

## 输出格式要求

默认输出普通 Markdown 正文。

用户通常会直接复制给 Codex，因此输出必须可直接复制。

不要在最外层包裹 ```markdown。

内部尽量避免嵌套 ```text、```sql、```java 代码块。

路径、类名、方法名、字段名、SQL 片段、枚举值使用行内反引号。

## 计划生成前置检查

生成计划前必须检查：

- 需求目标是否唯一
- 修改范围是否明确
- 是否存在必须先确认的不确定点
- 是否涉及表结构 / Liquibase / 索引
- 是否涉及权限 / 金额 / 出账 / 状态流转
- 是否涉及历史补偿
- 是否涉及外部接口
- 是否需要先做代码调查

如果存在阻塞性不确定点，必须先输出问题，不要直接生成执行计划。

## 全局执行规则

以下规则适用于所有轮次：

1. 不允许边分析边修改。
2. 每一轮只能处理本轮目标。
3. 分析深度优先于修改速度；允许扩大分析范围，不允许扩大修改范围。
4. 分析阶段可以查看任意调用链和数据链路；实施阶段只能改本轮确认范围内的文件。
5. 不允许顺手优化、重构、改名、抽方法、调整无关代码。
6. 不允许修改接口协议、表结构、索引、Liquibase，除非本轮明确允许。
7. 不允许修改无关文件。
8. 所有不确定点必须标记为“不确定”，不能猜。
9. 修改 SQL 前，必须先列出需要保持不变的业务口径。
10. 修改 LEFT JOIN、WHERE、GROUP BY、ORDER BY、分页、导出逻辑前，必须说明语义是否变化。
11. 原问题没有验证通过前，禁止处理新发现的问题。
12. 每轮完成后必须输出本轮 diff 的语义保护 review。

生成或更新多轮计划时：

- 每一轮都必须包含“当前轮完成条件”，明确交付结果、保持不变的语义、验证方式、预期结果、无法验证内容和人工验收条件；
- 全局执行规则必须包含“验证失败处理”，明确失败归因、当前轮最小修复、重新验证、范围外问题留证和环境受限时的人工步骤。

## 轮次数量规则

第 1 轮到第 5 轮是基础模板，不代表所有任务必须固定为 5 轮。

如果任务涉及报表、权限、金额、出账、结算、历史补偿、Liquibase、索引、外部接口等高风险内容，必须按风险类型继续拆分更多轮次。

不允许为了套用固定 5 轮模板，把多个互不相关或风险类型不同的改动合并到同一轮。

- 梳理当前调用链路和数据链路。

### 禁止范围

- 禁止修改代码。
- 禁止格式化代码。
- 禁止新增文件。
- 禁止修改 SQL。
- 禁止修改 Liquibase。
- 禁止顺手修复发现的问题。

- 多语言逻辑
- 当前索引使用可能性

#### 创单 / 保存类

- 入参来源
- 页面选择数据
- 本地保存逻辑
- 下游接口入参
- 订单落库字段
- 结算落数字段
- 幂等逻辑
- 异常回滚逻辑

## 第 3+ 轮：高风险专项轮模板（补偿 / 配置 / Liquibase / 索引）

### 本轮目标

只处理已经确认必要的补偿、配置、Liquibase 或索引改动。

如果没有明确要求，本轮不执行。

补偿、配置、Liquibase、索引属于不同风险类型。如果同时涉及多种类型，必须拆成独立轮次，不允许在同一轮中混合处理。例如：

- 历史数据补偿单独一轮
- Liquibase / 表结构变更单独一轮
- 索引建议 / EXPLAIN 单独一轮
- 配置变更单独一轮

### 启动条件

只有同时满足以下条件，才允许执行本轮：

1. 已确认需要历史补偿、配置变更、表结构变更或索引变更。
2. 已确认文件路径或 Liquibase 文件路径。
3. 已确认影响范围。
4. 已确认回滚方式。
5. 如果是索引变更，必须已有核心 SQL 的 EXPLAIN 结果，或者明确只输出建议不落地。

### 禁止范围

- 禁止在没有确认的情况下新增字段。
- 禁止在没有 EXPLAIN 的情况下直接新增索引。
- 禁止直接给不可回滚的 UPDATE。
- 禁止不带 WHERE 条件的数据修复。
- 禁止不带执行前 COUNT 和执行后核对的补偿脚本。

### 本轮输出要求

根据改动类型输出。

#### 历史补偿

必须包含：

- 执行前 COUNT
- dry-run 查询
- UPDATE / INSERT / DELETE 语句
- 幂等条件
- 分批策略
- 执行后核对 SQL
- 回滚 SQL 或回滚说明

#### Liquibase

必须包含：

- changeSet id
- author
- preConditions
- rollback
- 是否支持重复执行
- 是否限定 dbms
- 是否影响线上大表

#### 索引

必须包含：

- 核心 SQL
- EXPLAIN 结果摘要
- 现有索引
- 新增索引建议
- 为什么字段顺序这样设计
- 覆盖哪些查询场景
- 是否影响写入性能
- 是否建议直接落地

## 第 4 轮：验证与回归

### 本轮目标

只做验证，不做无关修改。

### 验证范围

至少包含：

- 单元测试
- 接口测试
- SQL 核对
- 权限验证
- 分页验证
- 导出验证
- 异常场景验证
- 历史数据核对
- 回归场景验证

### 输出格式

| 验证项 | 验证方式 | 预期结果 | 实际结果 | 是否通过 |
|---|---|---|---|---|
|  |  |  |  |  |

如果无法执行测试，必须说明原因，并给出人工验证步骤。

## 第 5 轮：Review 修复

### 本轮目标

只修复 review 或验证中明确发现的问题。

Review 修复轮每轮只能修复一个明确风险。如果 review 中发现多个互不相关风险，必须拆成多个修复轮。不得借 Review 修复轮处理新需求、顺手优化或重构。

### 禁止范围

- 禁止处理新需求。
- 禁止扩展优化。
- 禁止重构。
- 禁止修改未被 review 指出的代码。
- 禁止在一个修复轮里处理多个互不相关的问题。

### 输出要求

## 修复的问题

## 修改文件

## 为什么这是最小修复

## 是否改变原有语义

## 验证结果

## 特殊任务规则

### A. 报表任务

报表任务必须拆出：

1. 代码调查轮
2. 字段映射轮
3. 查询实现轮
4. 权限验证轮
5. 分页 / 导出 / COUNT 验证轮
6. 索引与 EXPLAIN 专项轮

没有真实 EXPLAIN 时，只输出索引建议，不直接改 Liquibase。

### B. 出账 / 结算任务

出账 / 结算任务必须拆出：

1. 展示链路
2. 创单链路
3. 订单落库链路
4. 结算落数字段
5. 历史补偿
6. 对账 / 财务报表影响

不能只修列表接口。

### C. 权限任务

权限任务必须拆出：

1. 当前权限框架调查
2. 字段别名确认
3. 可见权限影响
4. 数据权限影响
5. 特殊权限验证

### D. 外部接口任务

外部接口任务必须拆出：

1. 现有 client 调查
2. 请求参数封装

4. 幂等处理
5. 失败重试
6. 日志与告警

## 单轮执行控制 / Round execution guard

当任务已经被拆成多轮 Codex 任务，或者用户要求 Codex 执行某一个指定轮次时，必须使用本规则。

### 核心原则

1. 可以读取完整任务文档作为上下文。
2. 只能执行用户明确指定的当前轮。
3. 如果用户没有明确指定当前轮次，不能自行选择轮次执行，必须先询问用户要执行哪一轮。
4. 其他轮次只作为上下文，不允许提前实现。
5. 每一轮只能有一个主目标。
6. 当前轮完成后必须停止，等待用户 review，不允许自动进入下一轮。
7. 如果当前轮是调查轮、分析轮、代码 Review 结论输出轮，不允许修改代码；如果当前轮是 Review 修复轮，只有在风险已明确且允许范围已明确时才允许做最小修复。
8. 不允许修改当前轮允许范围之外的文件。
9. 不允许顺手重构、改名、抽方法、清理代码、优化无关逻辑。
10. 不允许修改接口协议、表结构、Liquibase、索引、权限口径、金额计算口径、状态流转、导出逻辑、定时任务逻辑，除非当前轮明确要求。
11. 如果当前轮范围不清楚，必须先停止并要求用户确认，不能猜测执行。

### 执行前必须输出

1. 当前轮名称
2. 当前轮唯一目标
3. 当前轮允许修改范围
4. 当前轮禁止修改范围
5. 当前轮涉及的现有代码路径和影响点
6. 不确定点，必须明确标记为“不确定”

### 执行后必须输出

1. 修改文件清单
2. 每个文件的修改原因
3. 保持不变的业务语义
4. 本轮是否涉及 SQL / 权限 / 金额 / 状态 / 导出 / 定时任务
5. 风险点
6. 建议验证方式
7. Git diff 摘要
8. 是否满足进入下一轮的前置条件建议，最终由用户确认
9. 如果本轮修改涉及业务逻辑、异常路径、外部调用、状态流转、金额计算、权限判断、SQL 条件变化、异步 / Job / MQ / 回调，最终输出前必须按 Logging Style Guard 和 Hly Code Comment Style 做一次检查；只检查当前修改范围，不允许扩大修改范围。最终回复只需简要说明检查结果。

### 当前轮完成条件

本轮必须明确：

- 应产生的代码、SQL、配置或文档结果；
- 必须保持不变的业务语义；
- 可执行的验证命令或人工验证步骤；
- 预期验证结果；
- 当前环境无法验证的内容；
- 可以进入人工验收状态的条件。

不得只以“代码已修改”或“编译通过”判断当前轮完成。

### 验证失败处理

当前轮验证失败时：

1. 不得声明当前轮完成；
2. 不得自动进入下一轮；
3. 先判断失败是否由当前 diff 引入；
4. 属于当前轮范围的问题，在当前轮内做最小修复；
5. 修复后重新执行受影响的验证；
6. 不属于当前轮范围的问题，只记录证据；
7. 不得顺手修复当前轮之外的问题；
8. 环境原因无法验证时，说明原因并提供人工验证步骤；
9. 不得用静态判断代替本来可以执行的测试或构建。

### 当前 diff 日志和注释收口

本轮修改代码后，最终输出前必须仅针对当前 diff 检查：

- 新增关键业务行为是否有必要日志；
- 现有日志是否足以定位新增分支；
- 是否存在静默失败、静默跳过或静默回退；
- 是否存在重复日志；
- 是否存在高频正常 `INFO`；
- 是否泄露敏感信息；
- 是否修改了本轮范围之外的日志。

同时仅检查当前 diff 中：

- 新增业务字段是否缺少必要注释；
- 新增数据库字段是否缺少 `COMMENT` 或 `remarks`；
- 新增 interface 方法是否缺少必要契约说明；
- 新增核心方法是否缺少业务说明；
- 已有注释是否因本次修改而失真；
- 是否存在编造语义或废话注释。

发现缺失时，只允许在本轮原有修改范围内补齐。

每个修改代码的子 Agent 负责检查自己修改范围内的日志和注释。

主 Agent 最终检查：

- 是否有 Agent 只完成业务代码而遗漏日志或注释；
- 新增字段是否缺少注释；
- 是否存在重复日志；
- 多个 Agent 的业务术语是否一致；
- 共享 DTO、枚举和数据库字段说明是否一致；
- 日志和注释是否超出任务范围。

该检查不新增轮次，不要求额外确认，不改变业务逻辑。

### 越界处理

如果 Codex 发现自己已经提前实现了后续轮次内容，必须停止并报告越界内容，不允许继续扩大实现范围。

如果用户要求修复越界内容，只能回退或调整当前轮之外的修改，不能继续做新功能。
