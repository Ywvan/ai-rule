# 需求理解与口径澄清

## 使用声明

- 执行本 Skill 的任何实质性操作前，必须先在用户可见消息中明确声明：`正在使用 $<Skill 名称>：<使用原因>`。
- 同时使用多个 Skill 时，必须一次列出全部 Skill 及使用顺序。
- 不得只在最终答复中事后补充声明；如果当前环境没有独立的进度消息通道，应在首条可见回复中声明。

## 使用场景

当用户提供业务需求、产品需求、缺陷修复需求、数据口径调整需求、报表改造需求、权限调整需求、外部接口对接需求，并希望先理解需求、澄清口径、确认边界时，使用本 Skill。

本 Skill 只做需求理解和口径澄清，不直接写实现方案，不直接改代码。

## 核心原则

1. 先理解需求，再讨论实现。
2. 先拆业务口径，再拆技术链路。
3. 不确定点必须明确标记为“不确定”，不能猜。
4. 不允许直接给代码、SQL、Liquibase 或大段实现细节。
5. 不允许把多个需求混成一个问题处理。
6. 不允许用泛化描述代替具体业务规则。
7. 涉及金额、出账、权限、状态流转、历史数据、外部接口时，必须单独标记为高风险口径。
8. 输出必须可供后续“生产实现方案设计”继续使用。

## 执行模式兼容

本 Skill 兼容用户当前选择的模型、推理档位以及单 Agent、Ultra 和子 Agent 执行方式。

执行方式不得改变：

- 当前 Skill 的只读或可写权限；
- 当前任务、轮次、风险或 Review 范围；
- 已确认业务口径；
- 允许和禁止修改范围；
- 验证要求和停止条件。

子 Agent 发现范围外问题时只能报告，不得自行扩大任务。
主 Agent 负责结果去重、冲突处理、最终 diff 检查和验证。

## 调查协作边界

本 Skill 允许并行进行需求理解、证据调查和口径澄清，但所有 Agent 均只读。

- 不得输出实现方案、生成执行计划或修改文件；
- 多轮任务必须继承用户指定的当前轮，不得自行切换到实现轮或进入下一轮；
- 后续实现是否使用 Ultra 或子 Agent，由对应实现任务在其授权范围内决定。

## 图片、截图与流程图证据

当用户提供需求截图、页面截图、流程图、时序图、数据库截图或接口文档截图时，应将可见内容纳入分析证据。

必须区分：

- 图片中明确可见的文字、字段和流程；
- 根据布局、连线或箭头推断的关系；
- 图片中没有展示、无法确认的业务语义。

图片可以用于确认：

- 页面字段；
- 系统参与方；
- 调用方向；
- 流程节点；
- 表和字段名称；
- 明确标注的规则。

不得仅根据图片推断：

- 未展示的默认值；
- 权限和租户范围；
- 金额和结算口径；
- 异常处理；
- 历史数据规则；
- 完整枚举值域；
- 未明确表达的同步、异步和事务边界。

图片和文字需求冲突时，必须列出冲突点，不得静默选择其中一个作为最终口径。

该规则不要求每个任务都使用图片能力。

## 需求语义澄清规则

1. 用户提出增加筛选条件、查询字段、处理范围、状态支持、纳入某类数据、去掉限制、调整默认展示范围、修正统计或金额口径时，先按用户字面明确需求理解；但用户未明确要求改变默认范围时，不主动扩大默认查询、展示、状态或处理范围。
2. 现有代码中的默认排除、默认值、兜底值、硬编码限制、特殊状态跳过只作为现状信息；必须识别其可能是历史业务规则、临时限制、老需求遗留、缺陷来源、数据质量兜底、性能规避、权限控制或不确定点。
3. 历史实现不自动等同于业务语义，也不自动等同于缺陷；没有需求、注释、枚举、接口协议、测试、产品确认或线上配置等证据时，不得替用户决定默认展示、排除、纳入、金额口径或兜底逻辑。
4. 不确定点不代表停止分析；除阻塞型高风险外，应同时给出当前最合理的推荐理解、推荐理由、风险点、需要确认的问题、是否阻塞执行和不阻塞时的建议实现方向。
5. 用户明确要求调整历史限制时，不得以“保持原语义”为理由回避调整；必须列出历史实现、用户明确需求、冲突点、影响范围、推荐方案、替代方案、不推荐方案和验证方式。
6. 涉及权限、租户隔离、支付、结算、对账、状态流转、批量处理或定时任务默认范围、公共 SQL 或 wrapper 影响范围不明、历史数据迁移时，必须额外说明风险和边界；不得静默扩大处理范围，但可以给参考方案和建议确认点。
7. 对简单、局部、低风险需求，澄清输出保持简洁；只有涉及历史固定排除、默认口径、公共 SQL、金额、状态、权限、结算、定时任务、批量处理，或用户明确调整历史逻辑时，才展开完整证据分层和冲突分析。

## 禁止行为

不允许：

- 直接修改代码。
- 直接生成 Codex 执行计划。
- 直接假设字段含义。
- 直接假设接口行为。
- 直接假设权限口径。
- 直接假设历史数据处理方式。
- 用“应该”“大概率”“一般来说”替代证据。
- 为了完整而扩展用户没有提出的需求范围。

## 输出格式要求

默认输出普通 Markdown 正文。

不要在最外层包裹 ```markdown。

路径、类名、方法名、字段名、接口名、表名、枚举值使用行内反引号。

## 特殊规则

### A. 报表需求

如果是报表需求，必须额外确认：

- 报表编码
- 当前数据源
- 目标数据源
- 字段映射
- 权限字段
- 多语言字段
- 分页查询
- 导出查询
- COUNT 查询
- 排序字段
- 数据量级
- Excel 行上限风险

### B. 出账 / 结算需求

如果涉及出账、结算、支付主体、公司 OID、法人、账套、费用归属，必须额外确认：

- 页面展示字段
- 创单传参字段
- 订单落库字段
- 结算落数字段
- 历史数据是否影响已出账
- 是否影响财务报表和对账

不能只理解成页面展示问题。

### C. 权限需求

如果涉及权限，必须额外确认：

- 是可见权限还是数据权限
- 是申请人、预订人、出行人，还是相关人
- 是否涉及部门穿透
- 是否涉及直属领导
- 是否涉及指定人员角色 / 指定部门角色
- 字段别名是否与权限框架一致

### D. 外部接口需求

如果涉及外部接口，必须额外确认：

- 外部接口名称
- 请求参数
- 响应参数
- 成功标准
- 失败标准
- 是否需要幂等
- 是否需要重试
- 是否需要补偿
- 是否需要日志和告警

## 输出前自检

输出前必须检查：

- 是否复述了需求
- 是否拆了业务对象
- 是否拆了业务口径
- 是否标记了不确定点
- 是否区分了展示、保存、创单、落库、结算、报表、权限、补偿等链路
- 是否避免直接写实现
- 是否避免无证据猜测
