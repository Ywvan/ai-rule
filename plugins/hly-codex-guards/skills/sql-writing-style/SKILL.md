# SQL Writing Style

## 使用声明

使用本 Skill 时，简短说明正在应用 `$sql-writing-style`。

## SQL 影响分析

修改 SQL、公共 SQL 片段、公共 wrapper 或公共查询方法时，先确认它实际服务的查询类型和消费者。

重点确认是否关联：

- 列表与分页；
- `COUNT`；
- 导出；
- 汇总 / 统计 / 排行；
- 权限包装；
- 多租户条件；
- 批量处理、Job、对账或结算查询。

列表、导出、COUNT、汇总共用或部分共用逻辑时，应一起判断目标粒度和条件变化。公共片段的消费者尚未确认时，不直接把局部结果当成公共修改依据。

## 条件语义分类

分析 WHERE 条件时区分：

- 权限过滤；
- 租户隔离；
- 数据有效性；
- 业务筛选；
- 历史兼容；
- 数据质量限制。

不得把普通业务筛选放入权限公共 SQL，也不得把“参数为空则不限制”的规则套用到权限过滤或租户隔离。

### 可选筛选条件

新增普通查询 / 报表 / 列表的可选筛选字段时：

- 参数无值时不生成该筛选条件；
- 空集合和空字符串按调用协议处理，不自动转换成反向排除；
- 参数有值时才追加对应筛选。

该规则不自动适用于权限、租户、状态推进、支付、结算、金额、Job 或批量处理范围。

### 固定排除条件

遇到以下结构时，不因其“历史存在”自动认定必须保护，也不因其看起来奇怪自动删除：

- `!=` / `<>`；
- `NOT IN`；
- `IS NULL OR ... != ...`；
- 固定状态 / 类型 / 来源黑名单；
- 硬编码排除场景。

需要识别它属于明确业务规则、历史限制、权限 / 数据隔离、数据质量处理还是其他真实用途，再决定是否保留或调整。

## 数据粒度与 JOIN

SQL 修改或 Review 时优先确认：

- 目标结果一行代表什么；
- JOIN 两侧基数；
- 是否存在 1:N / N:M 数据膨胀；
- 聚合、去重是否掩盖 JOIN 膨胀；
- `LEFT JOIN` 右表条件放入 `WHERE` 后是否改变保留语义；
- 金额、数量、统计值是否因重复行被重复累计；
- 分页排序是否稳定且能唯一确定顺序。

## 写法约定

### 优先直接结构

优先使用能够直接表达业务关系的：

- `SELECT`
- `JOIN`
- `WHERE`
- `GROUP BY`
- `ORDER BY`

不要为了形式拆成多层结构。

### CTE

CTE 适用于：

- 表达明确业务步骤；
- 消除真实重复逻辑；
- 相比嵌套查询明显提升可读性。

单次使用且没有提升可读性的 CTE、多层嵌套 CTE、把简单查询机械拆成多个 CTE，默认不采用。

### DISTINCT

使用 `DISTINCT` 前明确重复来源。不要把 `DISTINCT` 当作未知 JOIN 膨胀的通用修复手段。

### 窗口函数

窗口函数适合排名、TopN、分组内去重、累计计算等需要窗口语义的场景。普通聚合能够清晰完成时，不为了技巧性改成窗口函数。

### 防御性函数和类型转换

`COALESCE`、`NVL`、`IFNULL`、`CAST`、`CONVERT` 等只在目标 SQL 的空值或类型语义确实需要时使用，不为“未来可能需要”主动增加。

### 嵌套查询

能够用清晰 JOIN / 聚合直接表达时，不增加无意义的多层子查询。

### Alias

别名应能对应真实表或业务对象。短别名如 `u`、`o` 可用于语义明确的查询；复杂查询避免连续使用 `a`、`b`、`c`、`t1`、`t2` 等无法辨识来源的别名。

## SQL Review 补充项

SQL Review 除通用 Review 结论外，重点指出：

- 目标粒度是否变化；
- JOIN 是否产生数据膨胀；
- 条件位置是否改变 LEFT JOIN / 权限 / 租户语义；
- 聚合 / 去重是否改变口径；
- 分页是否稳定；
- 公共 SQL 修改是否遗漏消费者；
- 是否存在有明确现实影响的不必要复杂度或性能问题。

CTE、子查询、窗口函数、`DISTINCT` 或某种函数写法本身不是 Finding。

## 输出

生成 SQL 时优先给最直接、可维护且符合当前目标语义的版本；只有存在真实取舍时再说明替代方案、影响范围或性能差异。
