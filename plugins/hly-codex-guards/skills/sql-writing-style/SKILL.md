# SQL Writing Style

## 影响范围与结果语义

先确认当前 SQL、公共片段、wrapper 或查询方法的实际消费者。仅当逻辑被共享、部分共用或消费者尚不明确时，扩展核对列表/分页、COUNT、导出、汇总/统计/排行、权限、多租户、批量/Job/对账/结算等可能消费者；已经确认是单一局部消费者时，不为完整性继续搜索无关调用方。公共逻辑消费者未确认，不以局部结果作为公共修改依据。

修改或 Review 时确认：一行代表的业务对象、JOIN 两侧基数及 1:N / N:M 膨胀、聚合/去重是否掩盖重复、金额/数量/统计值是否重复累计、LEFT JOIN 右表条件进入 WHERE 后的保留语义，以及分页排序是否稳定且唯一确定顺序。

## 条件边界

区分权限、租户隔离、数据有效性、业务筛选、历史兼容和数据质量条件；普通业务筛选不得放进权限公共 SQL。

普通查询/报表/列表的可选筛选：无值不生成条件，有值才追加；空集合、空字符串按调用协议处理，不自动变成反向排除。不得将这一规则套用于权限、租户、状态推进、支付、结算、金额、Job 或批量处理范围。

对 `!=` / `<>`、`NOT IN`、`IS NULL OR ... != ...`、固定状态/类型/来源黑名单或硬编码排除，先确认其业务、历史、隔离或数据质量用途；不因历史存在就保留，也不因形式奇怪就删除。

## 生产性能与执行安全

写入或 Review 可能进入生产执行的 SQL 时，同时考虑数据量/选择性、索引与列类型、调用频率和执行范围。信息不足时，不仅凭 SQL 文本断言“走索引”“不会全表扫描”或“可直接生产执行”，也不机械要求所有 SQL 执行 `EXPLAIN`；性能结论会影响方案时再核对 schema、索引、执行计划或实际数据规模，无法验证则说明。

- 过滤/JOIN 条件优先保持可利用既有索引的形式；列函数、`CAST` / 隐式类型转换、前导模糊匹配、跨类型比较等先结合索引、列类型和数据库能力判断，存在等价可索引写法时优先采用。形式本身不直接构成性能 Finding。
- JOIN、聚合、排序、窗口、子查询和深分页关注基数放大、中间结果、重复计算和返回量；小数据/低频场景不为理论性能重写，只有现实规模、调用频率或执行计划依据时才定性性能风险。
- `UPDATE` / `DELETE` / 回填 / 批处理确认过滤边界和预计影响范围；范围大或未知时考虑索引、锁、事务时长及是否分批、限速或可恢复。范围不足时不表述为可无条件直接生产执行。

## 写法约定

- 优先直接表达业务关系，不机械拆成多层 CTE 或子查询；简单、正确的 SQL 不为形式重写。
- CTE 用于明确业务步骤、消除重复逻辑或改善嵌套查询可读性；单次使用且没有可读性收益、多层嵌套 CTE 或机械拆分默认不采用。
- `DISTINCT` 前确认重复来源，不能掩盖未知 JOIN 膨胀；窗口函数只在排名、TopN、分组去重、累计等窗口语义适用时使用，普通聚合能清楚完成时不改成窗口写法。
- `COALESCE` / `NVL` / `IFNULL` / `CAST` / `CONVERT` 由目标空值或类型语义决定，不为假想未来需求增加。
- Alias 对应真实表或业务对象；简单查询可用 `u`、`o`，复杂查询避免无法辨识来源的 `a/b/c`、`t1/t2`。

## 输出与 Review

生成符合当前业务口径的直接、可维护版本；存在具体取舍时才说明替代方案及影响。Review 按上述范围和语义给出证据，指出漏掉的公共消费者、粒度/条件/排序错误或有现实影响的性能、复杂度问题；不另重复检查表。CTE、子查询、窗口函数、`DISTINCT` 或函数形式本身不是 Finding。
