# HLY Code Comment Style

## 总原则

- 使用中文注释。
- 注释用于帮助阅读者理解业务含义、特殊处理、维护风险和兼容约束。
- 优先保证代码命名清晰，不要用注释弥补混乱命名。
- 不要写太密，不要给每一行代码都写注释。
- 不要写“这行代码在做什么”这类重复代码语义的废话注释。
- 不要在注释中出现“AI生成”“Codex生成”等说明。
- 不确定业务含义时，不要编造注释；在回复中标注“不确定”。

## GPT-5.6 执行模式兼容

本 Skill 兼容普通、max、Pro、Ultra 和子 Agent 执行方式。

本 Skill：

- 不强制指定模型；
- 不强制指定推理强度；
- 不强制启用 Ultra；
- 不禁止 Ultra；
- 不强制创建子 Agent；
- 不禁止创建子 Agent；
- 不固定子 Agent 数量；
- 不覆盖用户的并发、深度或模型配置。

执行模式只影响任务的推理、委派和并行方式，不得改变：

1. 用户明确的任务目标；
2. 当前 Skill 的职责；
3. 当前任务的只读或可写状态；
4. 当前已确认业务口径；
5. 当前修改范围和禁止修改范围；
6. 当前轮次、风险编号或 Review 范围；
7. 高风险业务语义的确认要求；
8. 当前 Skill 原有的停止条件；
9. 当前任务的验证和输出要求。

不得因为使用 max、Pro、Ultra 或子 Agent：

- 扩大修改范围；
- 跳过调查；
- 跳过验证；
- 将推荐理解视为已确认事实；
- 绕过 Review 只读限制；
- 自动进入下一轮；
- 顺手处理任务范围外的问题。

## 子 Agent 委派规则

Codex 可以根据任务复杂度，将能够独立完成的工作委派给子 Agent。

主 Agent 委派时必须明确：

- 子任务目标；
- 调查或修改范围；
- 当前是只读还是可写；
- 当前轮次或风险编号；
- 已确认事实；
- 不确定点；
- 允许修改范围；
- 禁止修改范围；
- 需要返回的文件、符号、调用链或测试证据；
- 验收条件。

不得假设子 Agent 自动拥有主 Agent 的完整业务上下文和修改权限。

子 Agent 发现新问题时：

- 可以报告问题和证据；
- 不得自行扩展为新的修改任务；
- 不得修改当前子任务之外的问题。

主 Agent 负责：

- 汇总子 Agent 结果；
- 处理结论冲突；
- 去除重复结论；
- 检查修改范围；
- 统一业务术语；
- 统一检查最终 diff；
- 执行最终验证；
- 遵守当前 Skill 的停止条件。

### 当前 Skill 执行边界

- 主 Agent 和子 Agent 必须继承当前任务的只读或可写状态，只检查和修改各自已授权代码范围内的注释。
- 注释 Review 任务始终保持只读，不得为了统一风格修改当前 diff 之外的注释。

### 并行修改规则

当前任务本身允许代码修改时，可以将相互独立的实现工作委派给子 Agent。

并行修改必须满足：

1. 子任务职责清晰；
2. 修改范围可以明确归属；
3. 不得无协调地同时修改同一个文件；
4. 不得同时修改同一段业务逻辑；
5. 不得按不同业务口径修改同一链路；
6. 主 Agent 必须统一检查和验证结果。

以下共享内容必须指定单一修改负责人，或者由主 Agent 统一修改：

- 公共接口协议；
- 公共 DTO、VO、请求和响应结构；
- 公共枚举；
- 数据库表结构；
- Liquibase；
- 公共 SQL 片段；
- 权限和租户隔离；
- 金额、支付和结算口径；
- 状态机；
- MQ 消息结构；
- 公共基础组件；
- 多个模块共同依赖的配置。

不强制主 Agent 唯一写入，也不禁止 Ultra 的并行实现能力。

## 注释语言要求

使用业务语言描述原因。

避免使用团队黑话、架构黑话、互联网黑话。

禁止单独出现：

- 兜底
- 降级
- 收敛
- 兼容
- 特殊处理
- 防御性处理
- 历史逻辑
- 回刷
- 脏数据
- 幂等处理

必须说明：

- 为什么这样处理
- 不这样处理会出现什么问题
- 影响哪些数据

## 必须添加注释

以下位置生成或修改代码时必须补充必要中文注释：

- 新增类、核心方法、对外接口方法。
- Java `interface` 中新增或修改的方法声明。
- 复杂业务判断。
- 金额计算。
- 状态流转。
- 权限判断。
- 配置开关。
- 定时任务。
- 异步处理。
- 兼容历史数据的逻辑。
- 兜底处理。
- 不容易从代码看懂原因的特殊分支。
- 复杂 SQL 或有性能要求的 SQL。

## 不需要添加注释

以下位置通常不要添加注释：

- getter/setter。
- 简单字段赋值。
- 简单 if/else。
- 简单循环。
- 普通 CRUD。
- 变量名、方法名已经表达清楚的代码。
- 只是重复代码含义的注释。

避免无意义注释，例如：

- `@param userId 用户ID`
- `@param orderNo 订单号`
- `@return 查询结果`
- `@return 返回对象`
- `// 查询数据`
- `// 设置状态`

## 类注释

- 新增类必须写类注释。
- 说明这个类负责什么。
- 必要时说明这个类不负责什么，避免误用。
- 不写空泛描述。

示例：

```java
/**
 * 火车客付模式配置服务。
 *
 * 负责查询和保存租户的火车客付模式配置。
 * 不负责实际下单、支付和退款处理。
 */
```

## 方法注释

- 核心方法、对外接口方法、复杂业务方法必须写方法注释。
- Java `interface` 中的方法声明默认视为对外契约；新增或修改时必须写方法注释，说明该接口方法的业务用途、关键参数、返回值和特殊处理。
- 简单 CRUD 方法可以不写。
- 方法注释说明方法用来做什么。
- 对重要参数说明业务含义。
- 对重要返回值说明代表什么。
- 如果存在默认值、兜底值或特殊处理，必须写清楚。

示例：

```java
/**
 * 根据租户查询火车客付模式。
 *
 * 如果租户没有配置，返回默认客付甄选，保证历史租户下单逻辑不变。
 *
 * @param tenantId 租户 ID，不能为空
 * @return 火车客付模式；ZX 表示客付甄选，RAILWAY_12306 表示客付 12306
 */
public String getTrainGuestPayMode(Long tenantId) {
    ...
}
```

接口方法示例：

```java
/**
 * 分页查询企业码员工同步记录。
 *
 * 用于 CS 排查企业码员工同步结果，不触发重新同步或状态修正。
 *
 * @param query 查询条件，必须包含租户范围
 * @return 员工同步记录分页结果
 */
PageResult<AlipayEcPvtEmployeeSyncRecordResult> pageEmployeeSyncRecords(AlipayEcPvtEmployeeSyncRecordQuery query);
```

## 参数注释

- 不是所有参数都必须写注释。
- 参数含义明显时，可以不写。
- 参数不能为空、有特殊业务含义、会影响分支判断、容易和其他参数混淆、传错会影响原有业务逻辑时，必须写清楚。
- 不要写无意义参数注释，例如 `@param userId 用户ID`、`@param orderNo 订单号`。

## 返回值注释

- 不是所有返回值都必须详细写。
- 返回布尔值、枚举值、状态值、金额、计算结果时，必须写清楚。
- 返回值可能为空、可能返回默认值、会影响后续业务判断时，必须写清楚。
- 不要写无意义返回值注释，例如 `@return 查询结果`、`@return 返回对象`。

## 行内注释

- 行内注释只写在关键逻辑上方。
- 只解释为什么这样处理，不重复代码本身。
- 一个方法内行内注释通常不超过 3 处。

示例：

```java
// 历史租户没有该配置，默认走客付甄选，避免影响存量下单链路
if (guestPayMode == null) {
    return DEFAULT_GUEST_PAY_MODE;
}
```

## 字段注释

当前 diff 中新增或修改以下结构时，必须检查字段注释：

- Entity 字段；
- DTO、VO、Query、Result 字段；
- 配置字段；
- 枚举或状态字段；
- 金额字段；
- 时间或有效期字段；
- 布尔和开关字段；
- 外部接口请求和响应字段；
- 数据库存储字段；
- 计算字段；
- 历史兼容字段。

根据实际情况说明：

- 业务含义；
- 来源；
- 主要取值；
- 金额单位或计算口径；
- 时间语义；
- 默认值；
- 空值或历史数据处理方式；
- 外部协议含义。

字段名称和类型已经完整、无歧义表达含义时，不机械增加重复注释。

禁止编造需求、协议或代码中无法确认的字段语义。

示例：

```java
/**
 * 火车客付模式。
 * ZX：客付甄选；RAILWAY_12306：客付 12306。
 */
private String guestPayMode;
```

## SQL 和 MyBatis XML 注释

- 复杂 SQL 需要说明查询目的。
- 有分页、导出、大数据量查询时，需要说明主要过滤条件。
- SQL 依赖索引时，需要说明依赖的索引字段。
- 有性能要求的 SQL，需要说明扫描范围、索引依赖、绕开重型视图等关键原因。
- 不要给每个查询字段、每个 `select`、每个 `join`、每个 `where` 都写注释。
- XML 注释放在相关 SQL 片段附近，保持简短。

示例：

```xml
<!-- 按租户和结算时间分页查询，主要依赖 tenant_id + create_time 控制扫描范围 -->
<select id="pageSettlement">
    ...
</select>
```

## Liquibase 注释

- 优先用清晰的 changeSet id、表名、字段名表达意图。
- 只有迁移意图、历史兼容、回滚限制、数据回填假设、默认值或可空策略不明显时，才添加注释。
- 不要写重复 XML 标签含义的装饰性注释。

## 数据库字段注释

新增数据库业务字段时：

- MySQL DDL 必须有准确 `COMMENT`；
- Liquibase column 必须有准确 `remarks`；
- Java 对应 Entity 字段必须检查必要中文注释；
- 默认值、可空策略或历史兼容不明显时，应说明业务原因。

修改字段语义时，必须同步检查数据库和 Java 字段注释。

不得补全本次任务之外的历史字段注释。

## 特殊逻辑注释

- 历史兼容逻辑必须说明为什么兼容。
- 默认值逻辑必须说明默认原因。
- 兜底逻辑必须说明触发条件。
- 金额计算必须说明金额是否含服务费、退改费、手续费等。
- 状态判断必须说明关键状态的业务含义。
- 临时方案必须说明后续什么条件下可以移除。

## 密度控制

- 每个新增类建议 1 个类注释。
- 每个核心方法建议 1 个方法注释。
- 每个复杂方法最多保留 2 到 3 个关键行内注释。
- 不要为了凑数量添加注释。
- 优先用一个准确注释解释一个完整业务块，不要拆成多条碎片注释。

## 修改代码时的执行要求

- 生成代码时自动补充必要注释。
- 修改代码前先理解现有代码语义，再判断是否需要补充或调整注释。
- 修改代码时必须同步检查相关注释是否仍然准确。
- 删除本次修改范围内无意义、过期、错误的注释。
- 不要为了统一风格而清理无关文件或无关代码区域的注释。
- 优先写清楚业务意图，而不是解释代码语法。

注释应让一个半年后第一次接手该模块的开发人员，
不查需求文档也能理解为什么这么写。

如果注释仅说明“做了什么”，而没有说明“为什么这么做”，则视为无效注释。

## Final Comment Check

在完成代码修改或 review 前，必须检查当前 diff 是否存在以下注释问题：

- 新增业务字段是否缺少必要注释
- 新增数据库字段是否缺少 `COMMENT` 或 `remarks`
- 新增 interface 方法是否缺少必要契约说明
- 新增核心方法是否缺少业务说明
- 已有注释是否因本次修改而失真
- 是否存在编造语义或废话注释
- 金额计算是否缺少 WHY 注释
- 状态流转是否缺少 WHY 注释
- 权限判断是否缺少 WHY 注释
- SQL 条件变化是否缺少业务原因说明
- 异步、事务、补偿、幂等、重试、跳过逻辑是否缺少 WHY 注释
- 历史兼容、配置开关、外部供应商特殊规则是否缺少 WHY 注释
- 是否存在只解释“做什么”的废话注释

如果发现问题：

- 只允许在当前修改范围内修复
- 不允许扩大修改范围
- 不允许修改无关文件
- 不允许为了补注释制造废话注释
- 不允许改变原有业务逻辑
- 不允许改变接口协议
- 不允许改变 SQL 口径
- 不得补全当前 diff 之外的历史字段注释

最终回复只需简要说明注释检查结果，不需要输出完整检查表。
