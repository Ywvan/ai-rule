# HLY Code Comment Style

## 使用声明

使用本 Skill 时，简短说明正在应用 `$hly-code-comment-style`。

## 注释目标

注释优先解释代码本身无法直接表达的业务原因、来源、取值约束、默认行为、历史兼容或外部协议限制。

以下词语不能单独作为有效业务说明：

- 兜底；
- 降级；
- 收敛；
- 兼容；
- 特殊处理；
- 防御性处理；
- 历史逻辑；
- 回刷；
- 脏数据；
- 幂等处理。

使用这些概念时，需要补充触发条件、原因或影响。

## 类与方法

### 类注释

新增业务类时说明该类负责的业务职责；存在容易误用的边界时再说明“不负责什么”。

### 方法注释

以下方法新增或修改时，优先保留业务契约说明：

- 对外接口方法；
- Java `interface` 中的业务方法；
- 核心业务方法；
- 返回布尔、状态、金额或会影响后续业务判断的结果的方法。

注释应说明业务用途以及真正重要的参数、返回值、默认值或特殊行为。含义显然的参数不写 `@param userId 用户ID` 一类机械注释。

## 字段注释

当前 diff 新增或修改以下字段时，字段说明应覆盖容易被误解的业务语义：

- Entity / DTO / VO / Query / Result 的业务字段；
- 枚举、状态、布尔开关；
- 金额、比例、时间或有效期；
- 外部接口请求 / 响应字段；
- 数据库存储字段；
- 历史兼容或计算字段。

根据实际情况说明：

- 来源；
- 主要取值；
- 单位 / 金额口径；
- 时间语义；
- 默认值；
- 空值或历史数据行为；
- 外部协议含义。

Logger、依赖注入对象、无业务含义的临时字段和项目统一技术审计字段通常不需要重复业务注释。

## 行内注释

行内注释放在需要解释原因的业务块上方，不逐行翻译代码。

复杂方法通常保留少量关键行内注释；当一个方法同时包含多个独立业务规则时，可以分别说明，不以固定条数作为限制。

## SQL / MyBatis XML

复杂或性能敏感 SQL 的注释只说明真正重要的信息，例如：

- 查询业务目的；
- 目标数据粒度；
- 分页 / 导出的主要扫描范围；
- 必须依赖的索引或过滤条件；
- 某个不直观 JOIN / 条件存在的业务原因。

不要为每个 `SELECT` 字段、JOIN 或 WHERE 条件逐条加注释。

## Liquibase / 数据库字段

- changeSet id、表名、字段名已经清楚表达意图时，不增加装饰性 XML 注释；
- 迁移意图、历史兼容、回滚限制、数据回填假设、默认值或可空策略不明显时再补说明；
- 新增数据库业务字段时，MySQL `COMMENT`、Liquibase `remarks` 与 Java 字段说明应表达同一业务语义；
- 修改字段业务语义时，同步检查当前 diff 中数据库与 Java 侧说明是否仍然一致。

不得为了统一风格补齐当前任务之外的历史字段注释。

## 常见无效注释

以下注释通常应避免：

```text
// 查询数据
// 设置状态
@param userId 用户ID
@return 查询结果
```

如果名称和代码已经直接表达“做什么”，注释应补充“为什么、什么条件下、有什么业务约束”，否则不新增。

## Review 输出

注释专项 Review 只报告与当前 diff 直接相关的实际问题，例如：

- 关键业务契约缺少必要说明；
- 当前修改使已有注释失真；
- 字段来源、值域、金额 / 时间语义被错误描述；
- 数据库与 Java 字段说明出现语义冲突；
- 注释编造了代码和需求均不能支持的业务含义；
- 大量机械注释降低可读性。

最终只说明实际问题或“当前 diff 未发现明确注释风险”，不输出完整检查表。
