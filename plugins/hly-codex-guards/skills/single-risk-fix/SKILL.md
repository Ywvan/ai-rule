# Single Risk Fix

## 使用声明

执行本 Skill 的实质性操作前，简短说明正在使用 `$single-risk-fix` 处理一个已报告风险。不要用长篇流程说明打断任务。

## Goal

处理一个风险点，但不预设它一定成立。

流程只有三个判断：

1. 这个风险是否真实存在；
2. 如果存在，根因和最小修复是什么；
3. 修复后如何验证。

## 风险复核

Review Finding、风险编号、风险等级或其他 Agent 的结论都只能作为调查线索。

开始修复前：

- 重新读取相关当前代码；
- 验证问题是否真实存在以及实际触发条件；
- 必要时检查最少量的上下游调用、数据流、SQL、配置和测试；
- 如果问题依赖业务规则，再对照当前有效需求确认预期行为。

如果 Finding 不成立：

- 不修改代码；
- 明确说明原 Finding 为什么不成立；
- 给出能够支持结论的代码证据。

不要为了“修复一个已报告风险”而强行寻找替代问题。

## 修复原则

确认 Finding 成立后，只做恢复正确行为所需的最小修改：

- 不顺手重构、改名、抽方法或优化；
- 不修改无关文件；
- 不改变接口协议、数据库结构、返回结构、枚举或历史数据语义，除非用户当前任务明确要求；
- 允许读取必要上下游代码确认影响，但不机械“找全所有影响点”；
- 如果完成正确修复确实需要扩大修改范围，先说明原因和必须扩大的位置；
- 不得把未经验证的字段含义、金额公式、状态规则或业务比较方式自行补成事实。

## 验证

根据风险类型选择最直接的验证方式：

- 静态 diff / 调用链检查；
- 针对性单元测试；
- 编译或构建；
- 必要的集成验证；
- SQL / 数据验证；
- 关键正常、异常和边界场景。

验证失败时先判断是否由本次修改引入。范围外问题只报告，不扩展成第二个修复任务。

## 输出

默认使用直接、易读的中文。只说明：

- 风险是否成立；
- 关键证据；
- 修复方案或实际修改；
- 验证结果；
- 仍存在的风险或未验证项。

不要输出固定的兼容性矩阵、流程承诺或与当前风险无关的检查清单。
